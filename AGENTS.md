- Keep inspected upstream snapshots under `.lovable/migrate-external-project/github-source` as inert migration input; never import their bootstrap or run their scripts, because production auth, routing and tenant isolation use the existing TanStack/Supabase adapters.
- Port upstream pages and services individually, preserving the current club integrations and recording unverified capabilities in the migration ledger, because replacing the Base44 stack wholesale would break existing access and provider flows.
- Keep System Console selection in the URL and resolve it with `consoleSelection`; tenant management and the club portal must share that selection, while console access clears the active club data scope.
- Build the System Console sidebar from `getSaasAdminNavGroups` and use `layoutNavigation` for tab links and visibility; this keeps the imported console destinations synchronized and makes role-specific navigation testable.
- Old Base44 backend actions live in `src/legacy-functions/` (converted copies, registered in `registry.ts`) and run on the server through `invokeLegacyAction` with a Supabase-backed SDK stand-in (`_sdk.ts`); convert more actions the same way instead of hand-rewriting, because it keeps their logic identical to the source.
- Dev preview impersonation lives in `src/lib/devMock.js` and is gated by `import.meta.env.DEV`; it fakes only the signed-in user and club in the browser and never touches the database, so it cannot weaken access rules once published.
- Tryout desk name searches use `tryoutPlayerSearch` with separate club-filtered name queries; the compatibility adapter does not implement legacy `$or` filters.
- Team plan edits use `teamPlanSave` to update the existing identity and reuse its dues offer; copies omit plan, team and offer identities to avoid changing the original.
- Tryout guidance and team-plan readiness use `tryoutWorkflow` with explicit club ownership; roster dues actions open the existing wizard with an explicit team identity, because same-name teams and cached foreign plans must not select a different team's fees.
- Itemized team dues use shared `teamDues` validation and integer-cent totals in the wizard and checkout; fees persist on club-scoped plans and versioned offer configuration, and database triggers reject cross-club links so family inputs cannot select foreign fees or prices.
- Club connections (/settings/integrations, the only connections page) authorize via `is_club_manager` on the caller JWT (club owner/admin membership or an explicit `system_owner_grants` row), store credentials only through Vault RPCs (`integration_secret_put/get/delete`, service-role only) and use single-use `club_oauth_states` with one shared callback; never reintroduce plaintext secret tables or a generic platform-admin bypass, because only the service-managed owner grant may act across tenants.
- Stripe Connect webhooks live at the public TanStack server endpoint and verify raw-body signatures before resolving a unique stored account-to-club match; account-scoped API helpers use `stripeAccount`, because payload tenant IDs and unscoped platform requests must not select tenant data.
- Deno integration contract tests under supabase/tests run only on disposable localhost stacks with provider-worker egress denied and fake adapters; missing endpoints/schema fail prerequisites rather than passing mocked authorization, because production fixtures and real provider calls are unsafe.
- Module catalog reads use the separate service-managed system_owner_grants table and an invoker owner check; split write policies must never become ALL policies, because ALL would grant non-owner platform admins a SELECT bypass.
- Tenant module keys and page/entity/action mappings live in moduleRegistry; moduleAccess is shared by client and server and requires explicit console approval plus core access, because paid subscriptions and global plugins are not tenant authorization.
- Layout wraps tenant pages in TenantRouteGate and filters desktop/mobile menus from the same mappings; the legacy dispatcher verifies JWTs and mapped actions, and SDK add-on CRUD checks caller membership before service access, because hidden menus alone cannot enforce entitlements.
- Existing tenant data uses restrictive tenant_has_console_module policies and owner-only entitlement mutations; keep the helper SECURITY INVOKER and add matching policies when migrating new module tables, because caller-visible memberships/grants suffice without elevated reads.
- Render onboarding content icons through OnboardingIcon with a graphical fallback; content-provided icon strings must never appear as labels.
- Features screenshots are captures of existing app views with isolated demo data, stored as CDN asset pointers; never expose real tenant data in public screenshots.
- Public page addresses and slug routes (help/resources) are declared in LegacyApp's PUBLIC_ALIASES/PARAM_ROUTES, mirroring the original app's route table, because pages not listed there are login-gated by default.
- Signed-out legacy actions are whitelisted in src/lib/legacyPublicActions.ts (whole actions, specific sub-actions, or tryout-invite payments only), because the dispatcher otherwise requires a signed-in caller.
- Beacon posts are fanned out server-side by the `beacon-deliver` legacy action (in-app, plus email/SMS for Urgent) using the shared `beaconDelivery` rules, and channel reads rely on `beacon_team_accesses` rows written by `beacon-team-access`; recipient settings stay private to each person, so the browser must never resolve other people's preferences.
- Club vocabulary (names, positions, rating scale, criteria) lives in clubs.terminology and is read through useTerminology/mergeTerminology with built-in defaults, so blank or missing values never break labels.
- Returning-player intelligence lives in private season-keyed player_season_reviews and per-user player_coach_reviews; shared usePlayerRetention/PlayerRetentionReview surfaces serve scoring and rostering, while RLS and triggers enforce manager or membership-plus-protected player_review_staff access, same-club identity, own-coach writes and manager-only follow-up; editable coach profiles never authorize private reviews.
- Checkout processor choice goes through `resolvePaymentProvider` (club preference, then the owner-set app default in `platform_payment_settings`, then whatever is connected), because clubs may use Stripe or Echelon and an unconnected choice must never break payments.
- The five staff role dashboards compose presentation-only DashboardWorkspace primitives around their existing data and permissions, because role-specific triage and operational tabs must not introduce alternative authorization or data sources.
- Player tryout cards project only same-club, same-player registration logistics through playerTryoutCards; ClubIdentity validates the active club and team dues select an explicit season, because family screens must not expose staff advice or substitute another season's plan.
- Coach compliance status is computed by the pure helper in compliance and re-exported by useCoachCompliance; this keeps missing-data handling and requirement-key checks consistent and independently testable.
- Finance screens count money through `financeLedger` (status aliases, collected/late/scheduled, invoice candidates, net position), and the overdue queue is rebuilt server-side by `overdue-payments` sync authorized via `is_club_manager` or own-club finance role; this keeps dashboard cards and their destination tabs showing the same dollars without a platform-admin bypass.
- Public pricing reads the single `pricing_configs` row only through the `get_public_pricing` function (table reads and writes are owner-only) and both it and the System Console editor go through `normalizePricingConfig`/`calculatePricing`, and the founding-spot count comes from that row, so displayed prices and the calculator can never drift apart.
- Beacon team scope (which teams show in chat/calendar) is a per-user, per-club browser preference via `beaconTeamScope`; it only narrows what the database already lets someone read, never widens it. Tryout check-in/evaluation/offers in Beacon reuse the dashboard tab components so access rules stay identical.
- Return links, redirects and emailed links use `trustedOrigin`/`isTrustedOrigin` (app domains only), and user-triggered email actions go through `assertClubRecipients` plus `sanitizeEmailHtml`; this stops callers from redirecting off-site or emailing strangers.
- RLS helper functions (`has_role`, `is_club_admin`, `is_club_member`, `beacon_can_read`) live in the unexposed `private` schema; reference them as `private.*` in new policies and functions so they are not callable through the API.
- Custom reports are built through `ReportWizard` on `customReportLibrary` data sources; advanced filters go through `applyAdvancedFilters`, which only accepts fields the data source declares, so report filters cannot query undeclared columns.
- Echelon checkout uses the gateway's Three-Step Redirect (`echelon.server.ts`, `echelon-complete`, `/echelon-pay`) so card numbers post straight to the processor; orders are marked paid only after the gateway confirms the same order id and amount.
- Scheduled/bulk legacy jobs (charges, digests, reminders, outreach, reconciles) are in `OWNER_ONLY_ACTIONS` in the dispatcher, because a signed-in caller must never trigger card charges or mass email.
- Beacon attachments go to the private `beacon_files` bucket under `<club_id>/…` and are opened through short-lived signed links, because messages are club-private.
- Native push tokens are saved only through the authenticated `registerPushToken` server function (service-role upsert keyed by token, so a phone moves to whoever signs in); users can only read/delete their own rows, because tokens must never be writable for other accounts.
